# AI assistant sidebar

Open **Edit > AI assistant**. The assistant docks on the right of the slicer; drag its left edge to resize it. Close hides the panel and stops any active request, preserving the chat until **New chat** or application exit.

For the component architecture, request lifecycle, tool contracts and extension points, see [AI assistant integration and architecture](AI-Assistant-Architecture.md).

For a nontechnical overview of usage, features and future possibilities, see the [Snorca AI assistant product guide](AI-Assistant-Product-Guide.md).

## Chat workflow

- Type naturally; Enter sends and Shift+Enter adds a line. Replies stream into the conversation.
- Replies render headings, bold/italic text, lists, quotes, inline/fenced code and pipe tables. Tables with more than two columns become labelled rows in narrow sidebars. Code wraps to the available width. Mouse-wheel input over reply text scrolls the transcript. HTTP(S) links open in the browser only when clicked; raw HTML remains literal and Markdown image URLs never load remote content. This is a bounded native Markdown subset; unsupported formatting such as strikethrough remains literal.
- Add PNG/JPEG photos or screenshots with **+ Images**. Preview/remove draft attachments before sending. Sent images remain attached to their chat message and available in later turns.
- **Settings** holds provider, API key, model, the selected endpoint, and collapsed developer tools. OpenRouter remains the default; direct Anthropic, DeepSeek, BigModel, and BigModel (Coding Plan) are available. DeepSeek uses `https://api.deepseek.com/chat/completions` with `deepseek-flash` by default; its model field is editable. Provider or model changes start a new conversation. Provider and per-provider model choices survive restart. API keys are saved per provider and application data directory in the operating system credential store (Windows Credential Manager, macOS Keychain, or Linux Secret Service where enabled). Keys are not written to application preferences or project files. Clear a key and Save to remove it; storage failures are shown in Settings.
- The compact target selector offers **Object**, **Global process**, **Global filament**, and **Global printer**. Global scopes edit the corresponding shared preset without requiring any object, including on empty plates and projects with complex objects. The assistant can edit only the manually selected settings scope; it can inspect other scopes but cannot switch the selector itself. Process changes affect the current global process preset, filament changes affect the currently edited filament preset, and printer changes affect the current printer preset. No model selection is required: every user turn includes the active plate inventory, with stable object/instance IDs, names, dimensions and positions. A sole object is inferred automatically. With several objects, the assistant inspects and edits explicit object IDs based on the request; ambiguous intent is clarified in chat.
- One collapsed **Activity** row groups each reply's working status, intermediate assistant updates and tool calls. It updates in place while the assistant works, then shows the total tool count and any failed calls. Expand the row to inspect the sequence, and expand an individual tool to read the edit summary and raw arguments/results. The final answer streams outside the group; tool-free replies leave no empty activity row. The interface does not invent or display private reasoning.
- Automatic model, color and setting edits update the slicer immediately in one cumulative **Live preview**. The assistant continues through the requested steps using fresh context after each change. One persistent **Apply changes / Dismiss** bar owns the whole preview: Apply keeps every step, while Dismiss restores the models, recipes and edited presets from before the first step. Apply does not execute an edit a second time. **Revert changes** remains available after acceptance.
- **Stop** or hiding the sidebar cancels the in-flight request and preserves completed preview steps for review or continuation. Partial tool arguments are never executed. Dismiss also cancels the request before restoring the checkpoint. **New chat** dismisses a pending preview before clearing history; accepted edits remain. Native editors/actions require a separate interactive handoff after the automatic preview is accepted or dismissed.

There is no automatic print submission. Slice normally after changes to inspect the result. Preset changes remain unsaved until saved in the normal preset UI. Native model Undo covers object changes, not preset configurations; use the inline Revert action for preset changes while the chat remains available.

## Tools and context

The model can call eight local tools:

| Tool | Behavior |
| --- | --- |
| `get_print_context` | Reads active-plate objects, current public settings and context identity; optional `object_id` targets an object without UI selection |
| `search_settings` | Searches the native catalog by key, label, category or description; optional `object_id` reads that object, and an empty query returns all settings |
| `get_slice_context` | Inspects the active plate's existing slice: warnings, estimates and optional toolpath statistics near a specified Z height |
| `read_gcode` | Reads a bounded, numbered excerpt of that slice's G-code, using its current `slice_id` |
| `propose_settings` | Validates settings and updates the cumulative live preview |
| `get_model_context` | Reads objects, parts, instances, bounds, selection, active plate geometry, text and physical/mixed filament IDs |
| `list_model_tools` | Returns operation schemas and availability of the native editors |
| `propose_model_operation` | Updates the cumulative model/color preview, or offers a native-editor handoff |

All user-facing editable FFF settings are discoverable through the native catalog: walls, infill, support, temperature, speed, acceleration, cooling, retraction, machine geometry and custom G-code. Credentials, internal preset bookkeeping, read-only fields and SLA settings are excluded. Changes target one scope per proposal. The selected filament target is the currently edited filament preset, not an arbitrary slot. Process/filament/printer changes may affect multiple objects and can be shadowed by plate/object overrides.

Object-scope print-setting proposals target a stable object ID on the current plate, independently of the UI selection. The target must have solid geometry and one instance. Multipart solid geometry and negative volumes are supported, including raised/engraved text. Settings modifiers, variable layer height, height-range/material overrides and part overrides other than extruder assignment remain unsupported by the settings tools. Model tools work independently of these settings restrictions, including multipart objects and multiple instances. The assistant receives dimensions, IDs, transforms, triangle counts, names, text, filament recipes and explicit images; full meshes are not transmitted. `get_model_context` identifies each instance's plate and includes a separate active-plate inventory. In Object scope, empty and multi-object plates expose shared settings as an explicitly read-only overview. Global preset scopes instead expose editable settings with an empty `object_id`, regardless of geometry or object count. Targeted inspection of objects with unsupported edit configurations still exposes base settings, part/height-range overrides and the reason editing is unavailable. Read-only overviews cannot be applied as changes; use a fresh targeted Object context or select a Global scope for shared preset edits.

The active plate inventory also reports slice availability. `get_slice_context` reads the completed native G-code processor result, including slicer warnings, toolpath conflicts/outside-bed flags, estimated time, material volume/mass/length and time by extrusion role. Supply `height_mm` to inspect a band around a reported failure height (`radius_mm` defaults to 0.5, maximum 20). The band reports move counts and extrusion speed, fan, nozzle temperature, line width, layer height and volumetric-rate ranges, plus up to 80 move endpoints and a G-code line range. Samples are the first matching moves in G-code order, not a complete reconstruction; repeated heights in sequential printing are included and moves are not attributed to individual objects.

`read_gcode` uses the application's current slice file and line index; it accepts no filesystem path. It returns up to 200 lines and 64 KiB of source text, with one-based line numbers and pagination. Individual lines are limited to 2048 bytes and explicitly marked when truncated. A changed slice/plate ID, missing or changed file, invalid line index or non-text data is rejected. Slice tools refuse data while a worker is active, updates are pending or the plate's slice is invalid. Saved slices whose toolpaths are not loaded report that Preview must be opened. Neither tool starts slicing or submits a print. After model/settings edits, slice again before inspecting the new result. These are planned paths and estimates, not evidence of physical print success or an automatically captured viewport image.

## Model editing and color mixing

Automatic, reviewed operations include move/rotate/scale/resize/mirror; drop to bed; cube, cylinder, sphere, cone, torus and wedge creation; editable raised/engraved text; duplicate/delete/rename; part-type conversion; filament assignment; face/box painting for color, supports, seams and fuzzy skin; split into parts; boolean union/difference/intersection; mesh simplification; plane cuts; mixed-filament creation and native color matching.

New standalone shapes default to the active plate's XY center, with their bottom on its bed surface. This uses the actual plate's world-space position, including offset plates in multi-plate projects. The assistant omits `position_mm` for ordinary shape creation; explicit positions remain supported and describe the shape's center in world coordinates. Shapes added as parts default to their parent object's center. Model context exposes the active plate's index, surface center and XY size.

For example: **Add “hello” centered on the top of this cube, 5 mm tall and 0.6 mm raised.** Text uses the bundled font and native emboss metadata, so the text editor can continue editing it. Automatic placement checks the actual surface and a planar footprint. Use the native editor for curved surfaces or precise interactive placement. Painting selects whole original triangles by face normal and optional world-space box; brush-level painting stays in the native editor. Boolean/simplify operations clear painting and text metadata on the replaced mesh. Heavy automatic geometry operations are limited to objects with at most 500,000 triangles.

The assistant can open every enabled native gizmo: move, rotate, scale, lay flat, cut, boolean, supports, seams, fuzzy skin, color painting, text, SVG, measure, assembly, simplify and brim ears. It also exposes variable layer heights, repair and the mixing dialog, plus native arrange/orient/split/merge/fill-bed/fit-to-bed actions. These handoffs retain native dialogs and interactive controls; opening an editor is not reported as a completed edit. Native availability checks still apply.

Mixes use actual project recipes and active virtual-filament IDs. Components must be loaded, compatible physical filaments, with percentages totaling 100. Layer-cycle and simple distributions, manual patterns and gradients are supported. Gradient endpoints express the first component's blend percentage, not height in millimetres. Color matching uses the native calibrated solver and marks its preview as approximate. A recipe can be assigned to an object or part, or used for surface painting in a subsequent operation.

Automatic edits are validated on copies and then committed to the live slicer as reversible preview steps. A single checkpoint and native geometry Undo snapshot span the sequence. Apply accepts the visible state; Dismiss/Revert restores the entire checkpoint, including edited process/filament/printer configurations and mixing recipes. Each continuation and final action checks a fingerprint that excludes selection and camera changes but includes model data, preset identities and values. Later manual edits are preserved: a conflicting preview cannot overwrite them. Mixed recipes and presets require the preview controls for complete restoration; geometry Undo alone does not restore project configurations. Unsaved previews are live project state, so saving/exporting the project includes what is currently visible.

For print-setting proposals, scalars retain their JSON types. Percent values are numbers; number-or-percent values accept an absolute number or a string such as `"120%"`. Arrays/points use JSON-encoded strings in setting proposal arguments (`"[215]"`, for example), while catalog values are actual arrays. Nullable vectors may contain null elements. Extruder and flow-variant array lengths stay unchanged; polygon point counts can change. Model-operation parameters use normal JSON arrays.

## Providers, images and limits

Defaults: OpenRouter `deepseek/deepseek-v4.1-flash-1017`, Anthropic `claude-sonnet-5-5`, BigModel `glm-5.3-flash`. Models must support tool calls and, for attachments, vision. OpenRouter requires endpoints that support the requested parameters. API usage is billed by the provider, and OpenRouter forwards requests to its selected model provider.

Choose **BigModel** for the standard API (`https://open.bigmodel.cn/api/paas/v4/chat/completions`) or **BigModel (Coding Plan)** for the coding endpoint (`https://open.bigmodel.cn/api/coding/paas/v4/chat/completions`). Paste the corresponding API key; the model field can be changed to another accessible GLM model, such as `glm-5.3`. The initial `glm-5.3-flash` model supports native images and tools according to [BigModel's model documentation](https://docs.bigmodel.cn/cn/guide/models/vlm/glm-5.3-flash). Coding Plan access depends on account eligibility and the provider's [supported environments](https://docs.bigmodel.cn/cn/coding-plan/tool/others); the integration does not imply provider approval of Snorca or automatically switch billing routes.

Up to four images can be attached per message, each at most 20 MiB and 40 megapixels. Header dimensions are checked before decoding. Images are resized to a maximum edge of 1568 pixels, flattened to RGB, and encoded as JPEG without original metadata, with a 4 MiB base64 limit per prepared image. Chat requests are limited to 32 MiB and bounded history; start a new chat when full. A user turn allows at most 32 model rounds and eight tool calls per response. A stopped or bounded run keeps its completed preview and can continue in the next message. Conversation history is bounded to 512 messages as well as the request byte limit. Stream responses are limited to 2 MiB.

Conversation messages, prepared image pixels, model/part names and lettering, filament recipes, slice summaries, requested G-code excerpts and tool-returned public settings, including custom G-code, go to the selected service. Original image filenames, the slice file's local path and full mesh data are not sent. Text embedded in settings, images or G-code comments may itself contain user information. G-code/comments and all tool output are treated as untrusted data. Transport uses fixed endpoints, verified TLS, no global slicer account/printer headers, and no redirects.

## Implementation and offline tools

`AIPrintAssistantDialog.cpp` now implements a native wxWidgets chat panel, owned by `MainFrame` beside its normal workspace. Its HTTP workers communicate through a mailbox and never retain GUI/model pointers. A UI timer consumes complete SSE events and updates the transcript. `AIPrintAssistantChat` adapts conversation history, multimodal messages, tool schemas/results and streaming protocols for all providers. Provider reasoning needed for tool continuations is retained in memory, separate from visible replies. BigModel's `reasoning_content` is returned verbatim in subsequent requests, with preserved thinking and streamed tool arguments enabled. BigModel and DeepSeek requests reserve 16,384 output tokens, including reasoning; OpenRouter and Anthropic retain the 4,096-token request budget. DeepSeek also preserves `reasoning_content` on tool continuations and later turns, using its official `thinking` parameter without BigModel-specific fields.

The system prompt and tool definitions remain fixed throughout a conversation. Each user turn carries its current plate inventory/context in a new message, so changing objects, settings, scope or images preserves the earlier conversation prefix required by Sonnet 5.5's signed thinking blocks. Provider/model changes start a new chat. HTTP and streaming errors show bounded provider explanations, including structured upstream errors wrapped by OpenRouter, with API keys and image data redacted; raw response dumps are not shown. An HTTP 400 alone does not establish a lack of tool or image support.

Tool execution occurs only after a completed, valid stream and successful HTTP response. Each tool reads fresh plate/configuration/geometry state. Settings tools resolve explicit object IDs against the active plate, never silently selecting the first object on a multi-object plate. Mutation tools verify their supplied context IDs, validate merged values and use native updates immediately for the live preview. Apply checks the complete preview fingerprint and keeps the resulting state. Extra preset changes introduced by UI normalization trigger rollback. Revert refuses to overwrite later edits and preserves unrelated changes.

**Settings > Developer tools** retains context export and raw proposal import for offline validation. Exports contain public settings/model context and schemas, plus image hashes rather than image pixels. Model export works even without a supported settings selection. Proposal documents are limited to 64 KiB. Settings proposals use schema version 1, exact context/object IDs, an outcome, explanation, and key/value changes. Model proposals contain `context_id`, `operation`, `object_id`, `volume_id` and a typed `parameters` object matching the discovered operation schema. Offline imports use the same live-preview path as provider tools; sequential imports accumulate under one Apply/Dismiss bar.
