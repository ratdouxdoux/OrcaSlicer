# Local-Z / Subdivide Mix Layer

This note explains how `Subdivide Mix Layer` generates object sublayers for mixed
filaments, and how the wipe tower is planned when those sublayers require extra
tool changes.

Relevant code:

- `src/libslic3r/PrintConfig.cpp`: user-facing options such as `dithering_local_z_mode`
- `src/libslic3r/MixedFilament.hpp` and `src/libslic3r/MixedFilament.cpp`: virtual mixed-filament rows and physical extruder resolution
- `src/libslic3r/PrintObjectSlice.cpp`: Local-Z planner, mask generation, sublayer plans
- `src/libslic3r/GCode.cpp`: clipping normal extrusion paths into Local-Z passes and emitting them
- `src/libslic3r/Print.cpp`: wipe tower preplanning for Local-Z tool changes
- `src/libslic3r/GCode/WipeTower2.cpp`: wipe tower geometry and toolchange G-code generation
- `src/libslic3r/GCode.hpp`: `WipeTowerIntegration` state used during G-code export

## Terms

- Physical filament: a real 1-based filament ID, from `1` through the physical
  filament count.
- Mixed filament: a virtual 1-based filament ID after the physical IDs. For
  example, with four physical filaments, the first enabled mixed row is ID `5`.
- Nominal layer: the ordinary sliced layer from `layer.print_z - layer.height`
  to `layer.print_z`.
- Local-Z pass, or sublayer: a `SubLayerPlan` for a smaller Z interval inside a
  nominal layer.
- Mixed mask: the XY polygons painted with a mixed virtual filament.
- Fixed mask: physical-filament painted areas that must stay tied to one
  physical extruder while Local-Z is active.
- Base mask: the rest of the layer after mixed/fixed masks are removed. It is
  mainly stored for debug output; G-code clipping computes the printable base
  from extrusion paths and the mixed-mask union.

## High-Level Flow

1. Multi-material segmentation builds per-layer, per-filament masks.
2. The Local-Z planner converts mixed masks into `LocalZInterval` and
   `SubLayerPlan` records on the `PrintObject`.
3. G-code export reads those plans, clips existing perimeter and optionally
   infill paths against the Local-Z masks, and emits the clipped fragments at
   each sublayer Z with the sublayer flow height.
4. If a wipe tower is enabled, the wipe tower is preplanned with the extra
   tool changes needed by those Local-Z passes.
5. During G-code export, Local-Z path passes run before the normal nominal-layer
   object loop, then the printer returns to the nominal layer Z and prints the
   remaining layer content normally.

The mesh is not resliced at every Local-Z sublayer. The slicer slices normal
layers first, creates ordinary extrusion paths, then clips those paths by XY
masks and changes their Z and flow height for each Local-Z pass.

## Planner Entry Points

The Local-Z plan is built from `apply_mm_segmentation()` in
`PrintObjectSlice.cpp`.

Before the plan is built:

- mixed painted segmentation is generated by the multi-material segmentation
  code;
- `apply_mixed_surface_indentation()` may expand or contract mixed masks;
- `apply_mixed_component_surface_offsets()` is skipped when
  `dithering_local_z_mode` is enabled, because Local-Z resolves color through
  sublayer height and tool order instead;
- when `dithering_local_z_whole_objects` is enabled, whole-object mixed wall
  masks are merged with painted overrides through
  `local_z_planner_segmentation_with_whole_object_mixed_wall()`.

`build_local_z_plan()` clears any old plan and exits unless:

- the segmentation layer count matches the object layer count;
- there is at least one physical filament;
- `dithering_local_z_mode` is enabled, or a gradient mixed row exists.

## Choosing Sublayer Heights

For each nominal layer, the planner records:

- `LocalZInterval::z_lo`, `z_hi`, and `base_height`;
- whether any mixed paint is present;
- where the interval's sublayer plans start in the shared plan vector.

The planner then finds active mixed rows on that layer and picks a dominant
mixed row by painted-mask area. The dominant row supplies the default pass-height
pattern unless the layer enters isolated multi-row mode.

Height bounds come from:

- `mixed_filament_height_lower_bound`, clamped to at least `0.01` mm;
- `mixed_filament_height_upper_bound`, clamped to at least the lower bound.

The chosen pass heights are always sanitized so they:

- are finite;
- stay within the lower/upper bounds where possible;
- sum back to the nominal layer height.

There are four main height-selection paths.

## Explicit A/B Heights

If `mixed_color_layer_height_a` or `mixed_color_layer_height_b` is set, the
planner repeats those preferred heights inside the nominal layer. The final pass
is adjusted to consume the remaining height. If the result cannot be fitted into
the bounds, it falls back to the automatic builders.

## Automatic Two-Color Local-Z

For ordinary two-component rows, the planner converts `mix_b_percent` into
target component heights between the lower and upper bounds:

- component A target height = lower + A percent * (upper - lower)
- component B target height = lower + B percent * (upper - lower)

It then builds an alternating A/B/A/B sequence. When only two passes are needed,
the order is kept stable across layers unless a gradient row intentionally
controls the order.

`choose_local_z_start_with_component_a()` compares the pass heights with the
target A/B heights and chooses whether pass 0 should be A or B. If both choices
are equivalent, it uses the row cadence index so equal splits do not flip
unnecessarily between layers.

## Gradient Rows

A gradient row (`gradient_enabled` with different components) builds a continuous
active layer run for that row. For each layer in the run, the planner linearly
interpolates `gradient_start` to `gradient_end` and computes A/B target heights
from the layer's position in the run.

Gradient Local-Z uses a fixed two-pass pattern. The implementation intentionally
assigns the first pass to component B and the second pass to component A, with
the pass heights swapped to match the desired gradient direction. This is why
gradient handling looks different from the ordinary A/B cadence path.

## Direct Multicolor Local-Z

When `dithering_local_z_direct_multicolor` is enabled, no explicit A/B heights
are set, and a mixed row has three or more physical components, the planner can
allocate sublayers directly across all components.

The component list comes from `gradient_component_ids`; weights come from
`gradient_component_weights` or default to equal weights. The pass-height builder
splits the nominal layer into enough bins to satisfy the weights within the
lower/upper bounds, capped by `local_z_max_sublayers` when that per-row cap is
enabled.

`build_local_z_direct_multicolor_sequence()` then chooses the physical extruder
for each pass. It tracks carry-over height error per component so small
rounding/fit errors are corrected across later layers.

## Multi-Row Layers

If more than one mixed row is active on the same nominal layer, and explicit A/B
heights are not set, the planner may use isolated multi-row mode. Each active
row gets its own pass-height sequence and dependency group, so independent
painted zones do not force one shared dominant cadence.

The planner stores `dependency_group` and `dependency_order` on each
`SubLayerPlan`. G-code export and wipe-tower preplanning use those fields to
keep dependent Local-Z passes in order while still minimizing tool changes.

## Building SubLayerPlan Records

For every split pass, the planner creates a `SubLayerPlan`:

- `layer_id`: nominal object layer index;
- `pass_index`: subpass order inside that nominal layer;
- `split_interval`: true for real Local-Z sublayers;
- `z_lo` / `z_hi`: sublayer bounds;
- `print_z`: the pass top Z, normally equal to `z_hi`;
- `flow_height`: sublayer extrusion height;
- `painted_masks_by_extruder`: XY masks indexed by zero-based physical extruder;
- `fixed_painted_masks_by_extruder`: fixed physical masks that participate in
  whole-object Local-Z handling;
- `dependency_group` / `dependency_order`: ordering constraints for grouped
  multi-row passes.

The target physical extruder for a pass is selected in this order:

1. direct multicolor sequence, if active;
2. strict A/B assignment from the active pair and start orientation;
3. fallback to `MixedFilamentManager::resolve()` with forced height-weighted
   resolution.

The selected mask is appended to `painted_masks_by_extruder[target - 1]`.

If the layer has mixed paint but only needs one pass, the planner still writes a
single `SubLayerPlan` with `split_interval = false`. This keeps cadence and
debug state consistent without asking G-code export to emit extra micro-passes.

## G-Code Emission For Object Sublayers

`GCode::process_layer()` reads each object's `local_z_intervals()` and
`local_z_sublayer_plan()`.

For each layer-to-print with a split Local-Z interval:

1. It builds `LocalZPassBucket` records from the interval's split plans.
2. Mixed masks are expanded by `LOCAL_Z_PERIMETER_MASK_EXPAND_MM` (`0.10` mm) so
   clipping catches perimeter fragments at the mask edge.
3. Base extrusion is clipped against the mixed-mask union, with a smaller
   `LOCAL_Z_BASE_MASK_EXPAND_MM` (`0.04` mm) guard.
4. Each Local-Z pass clips the existing extrusion collection to its pass mask
   through `clip_extrusion_collection_for_local_z()`.
5. Clipped paths get `flow_height` applied. `mm3_per_mm` is scaled by the ratio
   of new height to original path height.
6. Closed loops become clipped open fragments. The seam placer reanchors them
   near the normal seam location where possible.

Only perimeters are always included. Infill participates when
`dithering_local_z_infill` is enabled.

The Local-Z pass buckets are emitted before the normal layer's extruder loop:

- the printer changes to the pass extruder;
- it moves to `SubLayerPlan::print_z + z_offset`;
- it prints the clipped pass fragments;
- after all Local-Z passes, it returns to the nominal layer Z;
- the usual nominal-layer extruder loop prints support, base paths, and any
  non-Local-Z content.

If wipe-tower wiping overrides are active, Local-Z phase B is disabled for that
layer because those override paths are not Local-Z aware.

## Wipe Tower Planning With Local-Z

The wipe tower is planned in `Print::process()` during the wipe tower step.
`WipeTower2` is created in the normal way, with all physical extruder parameters
and normal layer tool ordering.

Before nominal tool changes are planned for a layer, the code checks whether the
same `print_z` has Local-Z passes:

1. `collect_local_z_wipe_tower_toolchanges()` scans `SubLayerPlan` records for
   matching object layers.
2. It compensates masks the same way as the G-code Local-Z path emitter.
3. It verifies that each pass mask actually intersects printable perimeter or
   enabled infill extrusion through `layer_has_local_z_extrusions()`.
4. It creates pass references containing the physical extruders needed by those
   Local-Z passes.
5. It sorts pass references by sublayer `print_z`, object index, and pass index.
6. If every pass has a dependency group, it uses the dependency scheduler.
   Otherwise it groups passes by equal sublayer `print_z` and uses
   `LocalZOrderOptimizer::order_bucket_extruders()`.
7. The result is a sequence of old-tool -> new-tool Local-Z tool changes.

Each Local-Z tool change is added to the wipe tower plan with
`WipeTower2::plan_local_z_toolchange()`. These are stored separately from normal
per-layer tool changes in `WipeTowerInfo::local_z_tool_changes`, but they still
contribute to `toolchanges_depth()` and therefore to the tower depth.

After Local-Z tool changes are preplanned, normal nominal-layer tool changes are
planned through `WipeTower2::plan_toolchange()`. This means Local-Z purges are
laid out on the same nominal wipe-tower layer before the ordinary tool changes
for that layer.

## Wipe Tower G-Code Generation

`WipeTower2::generate()` produces two result vectors:

- `tool_changes`: normal nominal-layer wipe tower tool changes;
- `local_z_tool_changes`: Local-Z tool changes to consume before the nominal
  object loop.

For each wipe tower layer, `generate()`:

1. calls `plan_tower()` so all normal and Local-Z toolchange depths contribute
   to the final tower depth;
2. emits Local-Z tool changes into `local_z_layer_result` first;
3. emits normal tool changes into `layer_result`;
4. calls `finish_layer()` so sparse infill/walls fill the remaining tower area;
5. stores both vectors on `Print::m_wipe_tower_data`.

`WipeTowerIntegration` receives both vectors. During Local-Z phase B,
`GCode.cpp` calls:

```cpp
m_wipe_tower->tool_change(*this, extruder_id, false, true, nominal_layer_z);
```

The `true` flag marks this as a Local-Z toolchange. `WipeTowerIntegration` then
tries to consume the next preplanned `local_z_tool_changes[layer_idx]` entry. If
the requested new tool and current tool match the preplanned entry, it emits
that wipe-tower G-code. The purge is performed at the nominal wipe-tower layer
Z, then object printing moves to the requested sublayer Z.

If the preplanned sequence does not match, the integration falls back to a
runtime path:

- use a reserved Local-Z tower slot if reserve boxes exist;
- otherwise perform a direct extruder switch without tower purge.

The reserve-slot path is implemented for safety, but the normal Local-Z color
blending path is the preplanned `local_z_tool_changes` path.

## Important Consequences

- Local-Z color blending is vertical stacking of physical colors inside the same
  XY mask. It does not create a new mixed material inside the nozzle.
- Sublayers are generated from existing nominal-layer extrusion paths. Geometry
  is clipped and flow height is changed; the mesh is not resliced per sublayer.
- The wipe tower remains organized by nominal layers. Local-Z purges are extra
  toolchange boxes on the nominal tower layer, not a separate tower layer for
  every object sublayer.
- With a wipe tower enabled, Local-Z phase B runs before the normal nominal-layer
  object loop so all micro-pass tool changes can be purged and printed before
  the rest of the layer.
- Without a wipe tower, Local-Z still emits micro-passes, but tool changes are
  direct `set_extruder()` changes.
- Manual mixed patterns and same-layer pointillism are handled by other
  distribution paths and are not Local-Z eligible.

## Debugging

When a Local-Z plan is built, `export_local_z_plan_debug()` writes:

- `local-z-plan-obj-<id>.json`
- `local-z-plan-obj-<id>-layer-<layer>-pass-<pass>.svg`

The JSON shows interval heights, sublayer counts, pass Z ranges, flow heights,
and mask counts. The SVG files show base masks and per-extruder painted masks.

Useful log messages include:

- `Local-Z plan start`
- `Local-Z interval`
- `Local-Z plan built`
- `Local-Z context`
- `Local-Z phase-b prepared`
- `Local-Z phase-b emitting`
- `Local-Z wipe tower preplan`
- `Wipe tower layer plan`
- `Local-Z toolchange emitted from preplanned wipe tower sequence`
